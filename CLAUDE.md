# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**PLEM** (Polygonal-Linear Extraction Metrics) — a research library with two halves: (1) `metrics/`, evaluation metrics for multiclass geospatial segmentation maps that contain point (0D), linear (1D), and polygonal (2D) features, and (2) `losses/`, differentiable training losses that let a single model learn to jointly predict all three feature types at once. The core evaluation problem `metrics/` solves: IoU is inappropriate for linear features because small positional offsets and width errors collapse the score even when the road centerline is correctly extracted. The paper's primary contribution (see `PAPER_OUTLINE.md` below) is now the `losses/` half — a differentiable multi-task loss whose geometric terms are direct analogs of three of `metrics/`'s own eval functions — with the eval metrics serving as both the design inspiration and the validation protocol.

All `metrics/`/`datasets/` inputs are 2-D NumPy arrays (`H×W`, dtype `uint8`). Label convention: `0` = background, `1` = road (linear), `2` = building (polygonal), `3` = point feature (small discrete objects — trees, lamp posts, manhole covers — spanning only a few pixels; optional, only used where the data actually has a point class). Tolerances are expressed in pixels; tie to ground sample distance (GSD) via `d = physical_metres / GSD_metres_per_pixel`. `losses/` uses the channel-index equivalent of this same convention on batched torch tensors — see below.

`PAPER_OUTLINE.md` (tracked in git, in progress) is a detailed 12-section outline for the project's ACM SIGSPATIAL paper draft ("PLEM: Polygonal Linear Evaluation Metric"). It restates every metric/loss formula and file:line snippet from this file plus proof sketches (Appendix A, eval metrics only) and complexity analysis (Appendix B, both eval metrics and `losses/`) — treat it as a secondary, paper-facing view of the library, not a source of truth (this file and the code remain authoritative). **Rewritten** to foreground the `losses/` training-loss contribution as a new §7 ("A Differentiable Multi-Task Loss for Joint 0D/1D/2D Extraction"), with §3–§6 (the eval metrics) reframed as "Evaluation Protocol" — both the design inspiration for the loss terms and the protocol used to validate them — and §8–§12 renumbered accordingly (old §7 Implementation → §8, old §8 Experimental Setup → §9, old §9 Results → §10, old §10 Discussion → §11, old §11 Conclusion → §12). §9.4/§10.4 (synthetic loss-ablation setup/results) and §9.5/§10.5 (real joint SpaceNet+Potsdam training run) are all now filled in with real numbers from this session's `tests/test_loss_sensitivity.py` and `train_unet_joint.ipynb` runs. §10.5/§11/§12 explicitly flag that no epoch-matched baseline comparison has been run yet (the joint run's 2 epochs vs. the baseline's 15 confounds any direct "is the new loss better" claim) — the highest-priority open item, not yet resolved.

## Architecture

### `metrics/` — the metric library

All public functions take `H×W` integer label maps and return dicts with named scalar fields (never bare scalars), making results easy to log and inspect.

| File | What it implements |
|---|---|
| `dtaf1.py` | **DTAF1** — primary unified metric. Per-class tolerance-radius F1 via `scipy.ndimage.distance_transform_edt`. The `class_config` dict maps `class_id → {name, tolerance}`. Class-agnostic: scoring a point class costs zero code changes, just add its entry to `class_config`. `dtaf1()` always computes and returns both `dtaf1_macro` (unweighted mean of per-class F1) and `dtaf1_weighted` (GT-pixel-count-weighted mean); the top-level `dtaf1` key is driven by the `reduction` param (default `"macro"`, unchanged/backward compatible). |
| `cldice.py` | **clDice** — centerline Dice for linear features. Skeletonizes both pred and GT via `skimage.morphology.skeletonize`, then measures mutual coverage. Zero-tolerant to positional shift; insensitive to road width. `cldice_multiclass()` per-class results carry an `"n_gt"` pixel count; `mean_cldice(..., reduction="macro"|"weighted")` mirrors `dtaf1`'s reduction API. |
| `boundary_f1.py` | **BF score** — boundary F1 for polygonal features. Extracts boundary pixels morphologically, then checks within-tolerance matches using distance transforms. Also exports `iou()` as the baseline comparator. `boundary_f1_multiclass()`/`mean_boundary_f1()` carry the same `"n_gt"`/`reduction` support as `cldice.py`. |
| `point_f1.py` | **Point F1** — tolerance-radius *instance* matching for point features (trees, lamp posts, manhole covers). Reduces each connected-component blob to a centroid (`scipy.ndimage.label` + `center_of_mass`), then does tolerance-restricted Hungarian assignment (`scipy.optimize.linear_sum_assignment`) between predicted and GT centroids — not greedy nearest-neighbor, which can lock a predicted blob onto the wrong nearby GT point when points cluster (see `TestPointInstanceMatching` for the adversarial case this avoids). |
| `unified.py` | **CBHM** — harmonic mean of mean clDice (linear classes) and mean BF (polygon classes); deliberately stays 2-way even when point classes are present (see below). `cbhm()` additionally always computes `cldice_mean_weighted`/`bf_mean_weighted` (within-type, GT-pixel-count-weighted) and `cbhm_soft` (a weighted *arithmetic* mean across linear vs. polygon types, using each type's share of total GT pixels as `type_weights`) — see "Area-weighting and zero-collapse" below. **`evaluate_all()`** — runs DTAF1 + CBHM, and optionally `point_f1_multiclass` if `point_classes` is passed, reported as an independent `point_f1_mean` figure; also surfaces `cbhm_soft` and `dtaf1_weighted` alongside `cbhm`/`dtaf1`. |
| `apls.py` | **APLS** (Average Path Length Similarity) — raster-skeleton connectivity/topology primitive for linear classes, added to close DTAF1's road-breakage blind spot (see below). No vector road graph exists anywhere in this pipeline (`datasets/common.py`'s `rasterize_lines` collapses roads to a flat pixel mask), so this approximates real APLS from raster skeletons only: skeletonizes pred/GT masks (`skimage.morphology.skeletonize`, as `cldice.py` does), builds an 8-connected pixel-adjacency graph via `networkx`, samples control-point pairs within the same GT connected component (grouped by source node so one `nx.single_source_dijkstra_path_length` amortizes across many pairs instead of one Dijkstra call per pair), snap-matches each GT control point to its nearest pred-graph node via `scipy.spatial.cKDTree` within a tolerance radius, and scores each pair by GT-vs-pred shortest-path-length ratio (0 if either endpoint is unmatched or no pred path exists). `apls_multiclass()`/`mean_apls()` carry the same `"n_gt"`/`reduction` support as `cldice.py`. |
| `dtaf1_topo.py` | **DTAF1-Topo** — connectivity-aware companion to DTAF1, additive/non-breaking like `dtaf1_weighted`/`cbhm_soft` (does not modify `dtaf1.py`). `dtaf1_topo()` calls `dtaf1()` unchanged, then for classes in `linear_classes` replaces plain per-class F1 with `harmonic_mean(f1, apls)` before macro/weighted-averaging; non-linear classes keep plain F1 (APLS has no defined meaning for polygon/point classes). Returns `dtaf1_topo`/`dtaf1_topo_macro`/`dtaf1_topo_weighted` plus the complete unmodified `dtaf1()` result under `"dtaf1_result"` for direct side-by-side comparison. **Not yet wired into `evaluate_all()` or `metrics/__init__.py`** — currently validated standalone against the synthetic `sweep_road_breakage()` sweep and `tests/test_metrics_sanity.py::TestRoadBreakageRegression` only (see below); real-data validation via `real_data_evaluation.ipynb`/`composite_vs_submetric_report.ipynb` has not been run yet. |
| `__init__.py` | Re-exports the main public API (`apls`/`dtaf1_topo` not yet included — see above). |

**Key design decision:** CBHM uses a harmonic mean so that failure on either feature type collapses the score to zero. DTAF1 uses a macro average, which is more lenient. Both are needed as foils. Point features are deliberately kept out of CBHM's harmonic mean (folding in an unbalanced 3rd class would blur that comparison) — `evaluate_all()` surfaces `point_f1_mean` alongside `cbhm`/`dtaf1`, never inside `cbhm`. Point matching also intentionally differs from DTAF1/clDice/BF: it works on discrete *instances* (via Hungarian assignment), not per-pixel tolerance, because point objects are numerous and pixel-based nearest-neighbor could double-count multiple GT points near one predicted blob.

**Area-weighting and zero-collapse (additive, non-breaking):** `dtaf1`'s default macro average and `cbhm`'s `cldice_mean`/`bf_mean` originally treated every class equally regardless of its GT pixel-area share, and `cbhm`'s harmonic mean collapses entirely to 0 if a single class scores 0 — even a sparse one next to an otherwise-perfect dominant class. `dtaf1_weighted` and `cbhm_soft` are additive companion figures that address this (`dtaf1`/`cbhm` themselves are unchanged, preserving the harsh-vs-lenient foil pairing above and all existing tests). `cbhm_soft` deliberately uses a weighted **arithmetic** mean, not geometric — geometric mean still collapses to exactly 0 whenever one input is 0, same as harmonic. See `TestAreaWeighting`/`TestSparseClassCollapse` in `tests/test_metrics_sanity.py` and the `sweep_class_imbalance`/`sweep_sparse_class_offset` sensitivity sweeps. **Caveat found on real data** (`notebooks/composite_vs_submetric_report.ipynb`, finding 2b): area-weighting only helps when the *failing* class is also the pixel-count *minority* within that tile. On `Khartoum_img371` (the tile motivating this fix — see below), the road actually has more GT pixels than the building despite covering a tiny share of the image's total area, so `cbhm_soft` only partially recovers (0.000 → 0.285) there, while it recovers much further (e.g. 0.48 → 0.85) on tiles where the building genuinely dominates by pixel count.

**Known limitation of DTAF1:** random pixel deletion (road breakage) is under-penalised because scattered remaining pixels still fall within the tolerance radius of GT pixels. Confirmed on real SpaceNet data in `notebooks/composite_vs_submetric_report.ipynb`: DTAF1 stays at 1.0 even with 75% of real road pixels deleted, while CBHM correctly collapses to ~0.57. **`dtaf1_weighted` does not fix this** — it also stays at 1.0 across all `road_dropout` severities, since area-weighting only changes how per-class scores are *combined*, not the per-pixel tolerance-matching logic within a class. The same notebook also found the opposite failure mode for CBHM: on a real, very sparse (~0.1% road-pixel) tile, a moderate road offset collapsed clDice (and therefore CBHM) to exactly 0 while DTAF1 degraded gracefully — clDice's skeleton-based comparison is brittle on short/sparse road segments. `cbhm_soft` softens but does not fully resolve this (see the caveat above). Neither composite is uniformly more trustworthy; check `cbhm`, `cbhm_soft`, `dtaf1`, and `dtaf1_weighted` together.

**`dtaf1_topo`/`apls` (metrics/apls.py, metrics/dtaf1_topo.py) close the road-breakage gap above, validated on synthetic data.** On the synthetic `sweep_road_breakage()` sweep (128×128, 4px road stripe, random pixel dropout), `dtaf1` stays pinned at 1.000 across nearly the entire fraction range exactly as documented above, while `dtaf1_topo`/`road_apls` collapse sharply starting around 30% dropout (0.938 → 0.397 → 0.057 → 0.010 by fraction 0.3/0.5/0.7) — even more aggressively than `cbhm`, since shortest paths across the fragmenting skeleton either lengthen sharply or disappear once the road disconnects. See `TestRoadBreakageRegression` in `tests/test_metrics_sanity.py` for the exact regression test. **This has not yet been validated on real SpaceNet data** (the real-data notebooks were not re-run for this change) and `dtaf1_topo`/`apls` are not yet wired into `evaluate_all()` — treat this as a validated-on-synthetic-data experimental addition, not yet a drop-in replacement for `dtaf1` in the consolidated report.

### `losses/` — differentiable multi-task training losses

Parallel to `metrics/` and `datasets/`, not a subpackage of either: pure `torch`, tensor-in/tensor-out on the standard PyTorch segmentation convention — `(B, C, H, W)` logits, `(B, H, W)` int64 label maps (channel index == class id, matching `metrics/`'s label convention) — **not** `metrics/`'s `H×W` numpy convention. Kept as its own top-level package deliberately: `metrics/`'s documented contract ("every public function takes `H×W` integer label maps and returns dicts of named scalars") is non-differentiable by construction (EDT, `skeletonize`, Hungarian assignment all break autograd), and adding torch code there would silently violate that invariant. Each `losses/` module is a differentiable analog of one `metrics/` eval function — mirrored in spirit and validated against the same behavioral properties (perfect→~0, width/offset insensitivity where the eval metric has it), never sharing code with its `metrics/` counterpart (numpy+scipy vs. torch tensors in an autograd graph can't share an implementation). No new dependency: everything is plain `torch`/`torch.nn.functional` (`max_pool2d`/`avg_pool2d`-based dilation/erosion, no `kornia`/`torchvision`).

| File | What it implements |
|---|---|
| `tolerance.py` | **`ToleranceBandLoss`** — differentiable analog of `metrics/dtaf1.py`. Precomputes a GT-side binary dilation-by-radius mask (`gt_tolerance_band`, under `no_grad` — GT is fixed, equivalent to `dtaf1.py`'s `dist_from_gt <= d`) and uses it as a static weight field against the model's soft probability map for the **precision** direction (needs only GT-side dilation, exactly as `dtaf1.py`'s precision does via `dist_from_gt`). The **recall** direction dilates the model's own continuous probability map directly via iterated `max_pool2d` (`soft_dilate_prob`) instead of a detached/stop-gradient hard threshold — since max-pool is differentiable, both precision and recall stay fully differentiable with gradients flowing into the model on both terms, with no approximation needed on either side. Takes the same `class_config` dict shape as `dtaf1.py` (`{class_id: {"name", "tolerance"}}`) — literally shareable between eval and training. |
| `boundary.py` | **`SoftBoundaryLoss`** — differentiable analog of `metrics/boundary_f1.py`. Reuses `tolerance.py`'s `soft_tolerance_pair_loss` primitive applied to a *soft boundary map* (`soft_boundary_map`) instead of the full class mask. The boundary map is the morphological gradient `dilate(x) - erode(x)` (reusing `cldice.py`'s soft erosion/dilation), which saturates to exactly 1.0 at a hard/confident edge — a close differentiable match to `boundary_f1.py`'s dilation-based `_extract_boundary`. **Do not** use `\|x - avgpool3x3(x)\|` for this (was tried and reverted): its peak response for a hard step edge is well below 1.0 (~0.56), which silently caps the achievable recall even under perfect alignment — caught by `TestSoftBoundaryLoss::test_perfect_prediction_near_zero`. |
| `cldice.py` | **`SoftClDiceLoss`** — differentiable analog of `metrics/cldice.py`, implementing Shit et al.'s soft-skeletonization (CVPR 2021, "clDice") directly: iterated `soft_erode`/`soft_open` via `max_pool2d`/`-max_pool2d(-x)`, fully differentiable, no `skimage.skeletonize` call. **Known limitation, unlike the hard eval-time version:** soft-skeletonization runs for a fixed `iters` (default 10), not to convergence, so width-invariance only holds up to whatever width that iteration count can fully erode away — validated up to a 3x width ratio by `TestSoftClDiceLoss::test_width_insensitivity`, the single most load-bearing new test (soft-skeletonization is easy to get numerically wrong in a way that still "compiles and returns a number"). |
| `heatmap.py` | **`PointHeatmapLoss`** — the training-side counterpart to `metrics/point_f1.py`, but **not** a differentiable relaxation of it: Hungarian assignment + connected-component labeling have no useful gradient path, so point supervision is reformulated entirely as dense Gaussian-heatmap regression (CenterNet-style). `gt_centroids_to_heatmap()` reuses the same `scipy.ndimage.label` + `center_of_mass` centroid extraction `point_f1.py`'s `_instance_centroids` already does at eval time, purely for target construction (under `no_grad`); overlapping GT points combine via elementwise max. `heatmap_focal_loss()` is the standard CornerNet/CenterNet penalty-reduced pixelwise focal loss. `point_f1.py`'s Hungarian matching is untouched and stays eval-only — a genuine, documented train/eval formulation mismatch, not papered over. **`gt_centroids_to_heatmap`'s `max_instances` cap (default 100):** its per-centroid Python loop does one full `(H,W)` Gaussian burn per instance — fine for real point-feature data (Potsdam crops top out around two dozen instances per tile), but a pathological, non-blob-like target (e.g. dense per-pixel noise — found while profiling `train_unet_joint.ipynb`'s integration, `torch.randint`-generated synthetic labels produced 8000+ connected components and stalled a single batch for tens of seconds) has no such bound. The cap drops excess instances beyond it with a one-time printed warning rather than silently stalling; real training data never hits it. |
| `multitask.py` | **`PLEMMultiTaskLoss`** — combines a CE+Dice base term (adapted from `train_unet.ipynb`'s `combined_loss`) with the three terms above, each independently weighted. Per-source class masking (e.g. SpaceNet tiles: road+building only; Potsdam tiles: building+point only — see `datasets/joint.py` below) is implemented by additively biasing a sample's masked-out class channels to a large negative logit **before** any softmax is taken (`_mask_logits`), not by post-hoc zeroing four separately-computed per-class losses: since every term is a function of softmax probabilities, driving a masked channel's pre-softmax logit to -inf makes its post-softmax probability — and therefore its gradient contribution to every term at once — vanish identically. One mechanism shared by all four terms instead of four bespoke masking implementations. Relies on target label maps never containing a class id a sample's source doesn't annotate, true by construction for both `datasets/spacenet.py` and `datasets/potsdam.py`. `forward()` returns a dict (`"loss"` plus each active sub-term as a detached float) — mirrors `metrics/`'s "always return a dict of named scalars" convention on the training side. |
| `__init__.py` | Re-exports `ToleranceBandLoss`, `SoftBoundaryLoss`, `SoftClDiceLoss`, `PointHeatmapLoss`, `PLEMMultiTaskLoss`. |

APLS/`dtaf1_topo` (graph shortest-path recomputation) have no differentiable analog here by design — no tractable lightweight relaxation exists — and stay eval-only permanently; this is a stated design decision, not a to-do.

### `models/` — shared model architecture

Just `unet.py` (`DoubleConv`, `SmallUNet` — extracted verbatim from `train_unet.ipynb`) plus `__init__.py`; both `train_unet.ipynb` (`num_classes=3`) and `train_unet_joint.ipynb` (`num_classes=4`) import from here so the two training runs share an identical backbone, making any baseline-vs-new-loss comparison between them apples-to-apples on architecture. ### `tests/`

- `test_metrics_sanity.py` — 50 pytest tests covering: perfect/null predictions, class isolation (missing road/building/point), road width insensitivity (IoU vs clDice/DTAF1), road offset tolerance, building erosion, monotonicity, point positional jitter tolerance, point instance matching (including the Hungarian-vs-greedy adversarial case), area-weighted reduction (`TestAreaWeighting`), sparse-class harmonic-mean collapse vs. `cbhm_soft`/`dtaf1_weighted` (`TestSparseClassCollapse`), APLS primitive edge cases (`TestAPLS`), `dtaf1_topo` composite structure and non-mutation of `dtaf1()` (`TestDtaf1Topo`), and the road-breakage regression proving `dtaf1_topo`/`apls` collapse where plain `dtaf1` stays high (`TestRoadBreakageRegression`).
- `test_losses_sanity.py` — 20 pytest tests for `losses/`, one class per module, each following: perfect prediction → loss ~0; degenerate empty-mask case → finite, no NaN/Inf; finite gradients + loss decreases after a few optimizer steps on a toy logits tensor. Plus `TestSoftClDiceLoss::test_width_insensitivity` (the width-invariance regression noted above) and `TestPLEMMultiTaskLoss::test_class_masking_*` (verifies perturbing a masked-out class's logits doesn't change the total loss or produce a non-negligible gradient, while unmasked classes still get a real gradient).
- `test_sensitivity.py` — standalone sweep script; also importable as a module. Exports `sweep_road_offset()`, `sweep_road_breakage()` (also reports `dtaf1_topo`/`road_apls` alongside `dtaf1`/`cbhm`, so the printed table directly shows the fix for DTAF1's road-breakage blind spot), `sweep_building_erosion()`, `sweep_road_thickness()`, `sweep_class_imbalance()` (now uses an imperfect road prediction so the averaging logic is actually exercised), `sweep_sparse_class_offset()` (reproduces the real `Khartoum_img371` CBHM collapse at small scale), `sweep_point_jitter()`, `sweep_point_dropout()`, `sweep_point_clutter()` — each returns a dict of lists suitable for plotting.
- `test_loss_sensitivity.py` — the `losses/` counterpart to `test_sensitivity.py`: same synthetic scenes/perturbation families (imports `SHAPE`/`make_road`/`make_building`/`make_gt`/`make_points`/`GT`/`POINT_COORDS` directly from `test_sensitivity.py` rather than duplicating them), but reports **loss value**, not accuracy, for a perturbed-prediction-vs-fixed-GT pair (via a "confidently peaked" logit encoding of the perturbed label map — see `_logits_from_label`'s docstring for why its confidence scale (4.0) is deliberately less extreme than `test_losses_sanity.py`'s `perfect_logits` (12.0): at scale 12, `PointHeatmapLoss`'s focal-loss log term saturates at its clamp ceiling for every "wrong" pixel, inflating a handful of false-positive point blobs to dominate a sweep's total by ~2 orders of magnitude — a test-harness artifact of unrealistically total confidence, not a property of real model output). Each sweep function (`sweep_road_offset_loss`, `sweep_road_breakage_loss`, `sweep_road_thickness_loss`, `sweep_building_erosion_loss`, `sweep_point_jitter_loss`, `sweep_point_dropout_loss`, `sweep_point_clutter_loss`) returns both 5 cumulative ablation columns (`ce_dice_only`/`plus_tolerance`/`plus_cldice`/`plus_heatmap`/`full`, for the printed table) and 4 raw per-term columns (`ce_dice`/`tolerance`/`cldice`/`heatmap`, for `--plot`'s small-multiples figures — the terms differ by orders of magnitude, so a shared axis flattens the non-dominant ones to invisibility). Confirmed story: `plus_tolerance` steps up right at DTAF1's 10px road tolerance boundary; `plus_cldice` shows correct zero-tolerance collapse under offset and stays flat up to ~3-4x road thickness (matching `losses/cldice.py`'s documented `iters`-bounded width-invariance) before rising sharply; `plus_heatmap`/`plus_cldice` are correctly flat (negative controls) in sweeps that don't touch their configured classes.

### `datasets/` — real-data acquisition and rasterization

Parallel to `metrics/`; produces plain `H×W` integer label maps from real public datasets, decoupled from `metrics/` (instance/centroid extraction stays in `point_f1.py`, not here).

| File | What it does |
|---|---|
| `spacenet.py` | Pulls SpaceNet (SN2 buildings + SN3 roads) from the public, unauthenticated `spacenet-dataset` S3 bucket. **Caveat:** SN2 building tiles (650×650px) and SN3 road tiles (1300×1300px) use different tiling grids even for the same city — `img{N}` is not the same tile between them. `build_spacenet_sample()` resolves this with a coarse-then-dense nearest-neighbor spatial search over tile centroids (tile ids are assigned in roughly raster-scan order, verified empirically) rather than downloading every building tile, and verifies the *rasterized pixel count* (not just a lon/lat bbox overlap, which can false-positive on merely-touching tiles) before accepting a match. |
| `potsdam.py` | Pulls ISPRS Potsdam (6cm/px, has real `Tree`/`Car` classes) via a Kaggle mirror, since SpaceNet has no point-object class and at its ~0.3-0.5m/px GSD objects like manholes/lamp posts would be sub-pixel anyway. Needs a one-time user-side Kaggle API token (`~/.kaggle/kaggle.json`) — not scriptable, see `load_kaggle_dataset()`'s docstring. Thresholds Potsdam's flat colored label rasters to a target class's palette color; **point classes** (`label_raster_to_point_mask`) connected-component labels blobs and filters by `min_area`/`max_area` (**known limitation:** touching instances of the same class merge into one connected component, no watershed splitting — real Potsdam "tree" blobs are sometimes contiguous canopy, not isolated point trees); **building** (`label_raster_to_building_mask`, added for `losses/`'s joint-training source — CLAUDE.md's `losses/` section) is a straight palette threshold with no CC/area filtering (buildings are large contiguous regions, not point instances — routing them through the point pipeline would wrongly split/drop real footprints). `label_raster_to_multiclass_mask` combines both into one building+point label map per tile; `build_potsdam_sample(extract_buildings=True)` builds this combined cache, `tile_potsdam`'s `min_building_pixels` param switches its crop-keep test to an OR condition (point OR building coverage, not both required) — default `extract_buildings=False` preserves the original point-only behavior exactly. Potsdam has no road/linear class in its 6-class palette at all. |
| `common.py` | Shared helpers: anonymous HTTPS download, geojson loading, lon/lat → pixel-space reprojection (`rasterio.warp.transform_geom` + inverse affine), `rasterize_polygons`/`rasterize_lines` (roads buffered by a physically-motivated width from each segment's `lane_number` property). |
| `joint.py` | Glue for joint SpaceNet+Potsdam training (needed since neither source alone annotates all three feature types: SpaceNet has road+building, Potsdam has building+point, neither has all three). `SOURCE_CLASSES = {"spacenet": [1,2], "potsdam": [2,3]}` is the single source of truth for which classes each source annotates; `class_mask_for_source(source)` returns the `(4,)` 0/1 array `losses/multitask.py::PLEMMultiTaskLoss` consumes directly as its `class_mask` argument. `load_joint_tiles()` loads every cached SpaceNet tile (`data/spacenet/<city>/*.npz`) and Potsdam tile (`data/potsdam/*.npz`, built with `extract_buildings=True`) into one tagged list, mirroring `train_unet.ipynb`'s existing `all_tiles` loading pattern. Pure numpy, no torch import, consistent with `datasets/`'s "decoupled from `metrics/`" contract. |

Downloaded/cached data lands under a gitignored top-level `data/` directory (curated sample: up to ~100 SpaceNet tiles across Vegas, Khartoum, Paris, and Shanghai — `spacenet_data_prep.ipynb` targets 25 tiles/city but the actual count depends on how many road-tile candidates pass the building-overlap filter per city — plus 15 Potsdam crops, now cached with `extract_buildings=True` so each `.npz` carries building+point labels, not point-only). No cloud compute needed — everything here is a local, curated sample fetched via plain HTTPS. Trained model checkpoints (see `train_unet.ipynb`/`train_unet_joint.ipynb` below) land under a top-level `models/` directory — `.gitignore` excludes everything under it *except* `*.py` (`models/*` + `!models/*.py`), since `models/unet.py` (the shared `DoubleConv`/`SmallUNet` architecture, extracted so both training notebooks use an identical backbone) is source, not a binary artifact, while the `.pt` checkpoints alongside it are.

### `notebooks/`

- `metric_comparison.ipynb` — synthetic-only demonstration: builds a 128×128 synthetic scene, runs all sanity checks, runs all sweeps (including the class-imbalance/sparse-class-offset section demonstrating `cbhm_soft`/`dtaf1_weighted`, and a section 3f rerunning `sweep_road_breakage()` to chart `dtaf1_topo`/`road_apls` collapsing sharply where plain `dtaf1` stays pinned near 1.0 — visual confirmation of the fix described below, cross-checked against `TestRoadBreakageRegression`), and renders a colour-coded summary table with pandas `Styler`. Kept synthetic-only by design; real-data work lives in the notebooks below.
- `loss_ablation.ipynb` — the `losses/` counterpart to `metric_comparison.ipynb`: synthetic-only, imports `tests/test_loss_sensitivity.py`'s sweep functions, renders the same small-multiples-chart-per-term + colour-coded summary table pattern (per-column `background_gradient`, not a fixed `vmin=0, vmax=1`, since loss values aren't bounded to [0, 1] the way eval-metric scores are). Confirms each new loss term encodes the geometric sensitivity its `metrics/` counterpart claims (Section 4's takeaway table cross-references which term should move vs. stay flat per sweep) before spending a real training run finding out.
- `spacenet_data_prep.ipynb` / `potsdam_data_prep.ipynb` — build and visually sanity-check the curated real-data samples (see `datasets/` above). `potsdam_data_prep.ipynb` now builds with `extract_buildings=True` and has a second visual sanity-check section (RGB / label map / colour overlay) for the building channel alongside the original point-centroid check — of the 15 cached crops, 14 have building coverage and 5 have point instances (3 have both), confirmed against the real Kaggle-mirror data in this session.
- `real_data_evaluation.ipynb` — applies the same perturbation families as `test_sensitivity.py`'s synthetic sweeps to real GT (there's no trained extractor in this repo, so "pred" is real GT run through offset/erosion/dropout/thickening/jitter/clutter at fixed severities) across the full curated sample, to see whether real, irregular geometry changes how a metric behaves compared to idealized synthetic shapes. Each sweep section has a markdown cell describing what its perturbations physically simulate (registration drift, network fragmentation, footprint erosion, missed/spurious point detections, etc.) and the severity units used, and is followed by a colorized small-multiples chart (metric value vs. severity, one subplot per perturbation, mean ± std band across the sample) using a fixed metric→color mapping shared across both the road/building and point-feature sections — solid lines are the harsh/unweighted `cbhm`/`dtaf1`, dashed lines are the area-weighted `cbhm_soft`/`dtaf1_weighted` companions, same color per metric pair.
- `composite_vs_submetric_report.ipynb` — compares each composite metric (CBHM, DTAF1) against its own sub-metrics on the real-data sweep results, flags the largest-divergence cases, and records findings (see the DTAF1/CBHM failure-mode note above, including the `cbhm_soft`/`dtaf1_weighted` mitigation and its `Khartoum_img371` caveat).
- `train_unet.ipynb` — PLEM's first real trained-model pipeline (everything above scores ground truth run through synthetic perturbations, not an actual extractor). Trains a small, CPU-only, single multiclass U-Net (3-level encoder/decoder, base=16 channels, one softmax head over bg/road/building) on 256×256 patches cut from the curated SpaceNet sample, split 70/15/15 train/val/test **at the tile level** (patch-level splitting would leak adjacent patches across the split and inflate held-out scores). Loss is class-weighted cross-entropy + soft Dice (background pixels vastly outnumber road/building). Test-tile predictions are stitched back from per-patch inference into full-size label maps and scored with `evaluate_all()`, then a handful of test tiles spanning the score range get 3-panel image/GT-overlay/prediction-overlay qualitative figures for human review. Checkpoints save to gitignored `models/unet_road_building.pt` (its `SmallUNet` architecture lives in tracked `models/unet.py`, shared with `train_unet_joint.ipynb` below). **Known limitation:** ~100 curated real tiles with no pretraining is a small dataset for segmentation — treat its test-set scores as a pipeline sanity check (train → predict → score → inspect all work end-to-end), not a benchmark result. Frozen as-is as the CE+Dice baseline for `train_unet_joint.ipynb`'s ablation.
- `train_unet_joint.ipynb` — the `losses/` counterpart to `train_unet.ipynb`: trains the same `SmallUNet` backbone (now `num_classes=4`, adding **point**) with `losses.PLEMMultiTaskLoss` on a **joint SpaceNet+Potsdam** source (`datasets/joint.py`), since neither dataset alone annotates all three feature types. Loads and per-source-splits (70/15/15, then concatenates) every cached tile, patchifies (each patch tagged with its source's `class_mask`), trains for a reduced epoch budget (`EPOCHS_JOINT = 2`, vs. the baseline's 15 — an explicit CPU-only time-budget scope choice), logs each loss sub-term per epoch (not just the total), and evaluates with `evaluate_all(..., point_classes=[3], dtaf1_config=<4-class config>)` — the first end-to-end exercise of `point_classes` on a real trained model's output. Checkpoints save to gitignored `models/unet_joint_4class.pt`. **Executed in this session against real data** (153 tiles: 123 SpaceNet + 30 Potsdam): all four loss sub-terms confirmed decreasing epoch-over-epoch (`heatmap` 0.346→0.010, a 35× drop); `point_f1_mean` confirmed non-`None` for 5/5 real stitched Potsdam test tiles; test-set aggregates (SpaceNet-only, n=19): `cbhm` 0.144±0.115, `dtaf1` 0.304±0.157 — both **below** the baseline's 15-epoch numbers (`cbhm` 0.316, `dtaf1` 0.440), read as an artifact of the epoch/task-difficulty gap (2 epochs vs. 15, on a harder 4-term joint task) rather than evidence about the new loss's quality, since no epoch-matched comparison has been run yet (highest-priority item in `PAPER_OUTLINE.md`'s Future Work). Qualitative review turned up a genuine real-data illustration of CBHM's harsh zero-collapse (`Appendix A.3`): the single worst-scoring tile by `cbhm` (`Vegas_img425`, `cbhm=0.000`) is visually one of the *better*-looking predictions, because `bf_mean=0.000` exactly despite `dtaf1_weighted=0.902` and `cldice_mean=0.474` both being high. **Known limitation found and fixed during integration testing:** profiling this run surfaced that `losses/heatmap.py::gt_centroids_to_heatmap`'s per-centroid Python loop has no bound on connected-component count, so a pathological (never-real) dense target could stall a batch for minutes — fixed with a `max_instances=100` cap (see `losses/heatmap.py`'s entry above). **Known limitation, unresolved:** SpaceNet/Potsdam are not resampled to a common GSD (a Potsdam patch covers much less physical area than a SpaceNet patch at the same pixel size) — no obvious failure mode observed, but untested rigorously.

All real-data notebooks (`spacenet_data_prep.ipynb`, `potsdam_data_prep.ipynb`, `real_data_evaluation.ipynb`, `composite_vs_submetric_report.ipynb`, `train_unet.ipynb`, `train_unet_joint.ipynb`) were run to completion at least once against the actual curated sample (not just written) — see their output cells for the executed results.

## Adding a new metric

1. Implement in `metrics/<name>.py`; return a dict with at minimum a scalar key matching the metric name.
2. Import and expose in `metrics/__init__.py`.
3. Wire into `evaluate_all()` in `metrics/unified.py` if it should be part of the consolidated report — decide deliberately whether it belongs inside an existing composite's formula (e.g. CBHM's harmonic mean) or should be surfaced as an independent figure alongside it (see how `point_f1_mean` was added as a precedent).
4. Add sanity tests in `tests/test_metrics_sanity.py` (perfect → 1.0, null → 0.0, class isolation).
5. Add a sweep function to `tests/test_sensitivity.py` and a notebook cell to `notebooks/metric_comparison.ipynb`.
6. If new dependencies are needed, add them to `requirements.txt`.
7. Commit and push the change (see "Workflow" below).

## Adding to `losses/`

1. Implement in `losses/<name>.py` as an `nn.Module` (or plain function) operating on `(B, C, H, W)` logits / `(B, H, W)` int64 targets; state in the docstring which `metrics/` file it's the differentiable analog of and what changed to make it differentiable.
2. Re-export in `losses/__init__.py`.
3. Wire into `losses/multitask.py::PLEMMultiTaskLoss` if it should be part of the consolidated training loss.
4. Add sanity tests in `tests/test_losses_sanity.py` (perfect → ~0 loss, degenerate empty-mask → finite, finite gradients + loss decreases after a few optimizer steps) — and, if the term claims a specific geometric invariance (e.g. width- or offset-insensitivity), a regression test proving it actually has that property, not just that it runs. Watch for the two failure modes already found here: (a) a soft mask formula whose peak magnitude never reaches ~1.0 silently caps precision/recall below their true value even under perfect alignment (`boundary.py`'s `avgpool`→`dilate-erode` fix); (b) testing gradient flow from a perfectly spatially-uniform starting point gives a false negative for any term that responds to local spatial variation (edge/boundary-type losses) — perturb the initial logits slightly instead.
5. Add a sweep function to `tests/test_loss_sensitivity.py` (compare its raw loss value across the standard perturbation severities, not accuracy) and a notebook cell to `notebooks/loss_ablation.ipynb`.
6. If new dependencies are needed, add them to `requirements.txt`.
7. Commit and push the change (see "Workflow" below).
